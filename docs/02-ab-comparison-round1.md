# 逆向记录 02 — A/B 对比第一轮（原版 vs ffmpeg，2026-11-22）

样本：`lianqu1980.mp4`（640x480 h264 29.97fps + AAC 44.1k，197.3s）
- 原版：`lianqu1980-128x128.amv` (14,691,237B)、`lianqu1980-160x120.amv` (17,672,631B)，30fps 档
- ffmpeg：`ff_128x128_15.amv` (6,468,958B)，15fps

## 完全一致（ffmpeg amvenc 就是照原版格式实现的）

| 项 | 双方 |
|---|---|
| 块序列 | `LIST(hdrl)>amvh` `LIST>strh(56全0)+strf` `LIST>strh(48全0)+strf` `LIST>{00dc,01wb}×N` |
| 容器 size 字段 | 全部写 0（RIFF/LIST 都不回填） |
| 奇数块 | 无填充字节，平铺扫描 |
| JPEG 帧 | 裸扫描数据：仅 FFD8/FFD9，**无 DQT/DHT/SOS/SOF**（量化表/Huffman/SOF 全固化在设备固件） |
| 音频块头 | `4B predictor + 4B 样本数(LE)`，样本数 = 22050/fps（15fps→1470/743B；30fps→735/376B） |
| 交织 | 视频帧与音频块 1:1 |

## 关键差异（重写版必须处理）

1. **`AMV_END_` 哨兵 + idx1 索引尾区**（重大发现）
   原版 = `…数据区… + 'AMV_END_'(8B) + 'idx1'(4B)+size(4B) + 索引记录×2N`
   ffmpeg 只写 `AMV_END_`，**不写 idx1** → 设备 seek 依赖 idx1，自研 muxer 必须补：
   - 记录 = `fourcc(00dc/01wb) + flags(0x10=关键帧) + 偏移 + 大小`，16B/条，音视频各一条
   - 偏移基准 = 数据 LIST 的 '00dc' 首块头起点（实测首条 offset=4=payload 起点−320）
   - 原版 idx1 size 字段 = 2×实际字节数（0x5C580=378240 vs 实际 189120）——照抄还是修正，待设备实测
2. **height=120**：原版正常输出 160X120（JPEG 帧同格式），ffmpeg amvenc 硬拒
3. **amvh dword0 = 1e6/fps（帧间隔微秒）**：原版 30fps→33333，ffmpeg 15fps→66667 ✔ 已解
4. **画质映射不同**：128x128 平均帧 2062B（原版 VFBS=high）vs 1426B（ffmpeg q≈1.6）→ 需逆向 quality→JPEG qtable 映射
5. **首个 01wb 的 predictor**：160x120 文件首块 predictor=`0000005b`（异常值，其余块全 0）——待查是否 logo/wave 相关

## 帧率机制（已解）

（如 128X128 候选 {16,25,30}）中最近的一个。源 29.97fps → 30 ✔ 解释第一轮样本。

## 临时文件管线（temp0.dat 残留已抓到）

`%TEMP%\temp0.dat` 与最终 .amv **逐字节相同**（14,691,237B，128x128 那次）。
管线：编码完整 AMV（含 AMV_END_+idx1 尾区）→ `%TEMP%\temp0.dat` → 复制到输出路径
（settings.ini `CopyFile=TRUE`）→ 中间文件 `idx1.dat`（盘符根，transdll 格式串 `:\idx1.dat`）被清理。
→ **抓法**：转换期间监视 `%TEMP%\temp0.dat` + 各盘根 `idx1.dat`，出现即 copy 走。
（idx1.dat 应是索引先落盘为独立文件、最后拼接——若能抓到可确认索引生成时机与 size 字段 2× 之谜）

## 第二轮捕获（15:07-15:08，三次崩溃样本，监视器全抓到）

### idx1.dat 中间文件格式（完全解开）

- 转换期间写在**盘根**（监视器在盘根抓到 4104→40968B 递增序列，每 ~16KB 刷一次）
- 文件 = `'idx1' + u32 size(写时恒0，最终装配时回填) + 记录×N`
- 记录 16B = `fourcc + flags(0x10) + 偏移 + 大小`（**标准 AVI idx1 布局**，偏移基准=数据区首块头）
- 最终 .amv 尾部 idx1 的 size 字段 = 记录数×32（**2× 实际字节数**，原程序 bug 被设备兼容）

### 崩溃模式（第二轮修正：与流对齐无关，是解码器兼容性）

| 文件 | 崩溃点 | 特征 |
|---|---|---|
| testsrc(坏trim) ×3 | 1410帧/3,399,243B | 视频37.5s音频197s |
| test16.mp4 (x264 High, bf=2) ×3 | **1410帧** | 30s 对齐 |
| test14.mp4 (x264 High, bf=2) ×3 | **1560帧** | 30s 对齐 |

- 崩溃点**按源确定性复现**，与磁盘(268GB free)无关
- amvh 恒 30fps（dword0=33333, 735样本）→ 理论 B（恒用最大候选帧率，低帧率源复制补齐）占优
- 1410帧@30fps=47s > 源时长30s → 工具复制帧续流，在源特定帧位置解码失败
- 原 lianqu1980.mp4(High) 全长成功 vs 我的 High 重编码在 47s 炸 →
  嫌疑=x264 码控产出的特定帧（复杂 B 帧金字塔/加权预测？）超出捆绑 ffmpeg 0.11 能力
- **判别实验**：`test16_b.mp4`/`test14_b.mp4`（Constrained Baseline, bf=0, MP3音频）
  - 若 b 版成功 → 解码器兼容性实锤，16fps 非整除策略可从 b 版输出读取
  - 若 b 版仍炸 → 工具对"非整除帧率复制"路径自身有 bug（重大逆向线索）

### 帧率吸附理论 → B 实锤

16fps/14fps 源（b 版成功转换）产出 amvh 全部 = **30fps、735 样本/块**。
**工具恒用该分辨率最大候选帧率**（128X128→30），低帧率源靠复制帧补齐；
ini 里 16;25 候选值形同虚设（UI 也无帧率项）。非整除音频策略问题不存在——永远是整除的 30。

附带发现：30s 源 → 870 帧 = **29s 输出**（丢尾秒，floor 行为）。

### +52 字段（amvh tail dword2）行为规则

| 源 | 音频 | +52 |
|---|---|---|
| lianqu1980.mp4 (197s) | AAC | 785 |
| test16.mp4 (30s) | AAC | 785 |
| testsrc坏trim (197s) | AAC | 785 |
| test16_b.mp4 / test14_b.mp4 (30s) | **MP3** | **29** |
| lavfi 1s | PCM | 1 |

- MP3/PCM 源：+52 = **输出时长秒数**（29=870/30，1=15/15）✔
- AAC 源：恒 **785**（与时长无关）= 工具 AAC 预扫描失败的哨兵值
- 重写版规则：写输出秒数；AAC 输入不再复制 785 这个 bug

### 崩溃机制（原工具真 bug，重写版须规避）

崩溃三要素：**AAC 音频 + 低帧率源（触发复制路径）**。
test16.mp4(AAC,16fps) 在 1410 帧炸——但预期总帧仅 ~900（30s×30fps）！
工具复制帧时音频计数错误，超发 510 帧后撞上流耗尽 → "编码器错误"。
lianqu1980(AAC,29.97fps) 不触发复制 → 成功。b 版(MP3,16fps) 计数正确 → 成功。
（+52=785 哨兵与崩溃同根：AAC 处理路径弱）

## 用户两问（初步答案）

- **AMV vs AVI 模式**：AVI 模式有独立 `AVI_EncDLL.dll` + ini 里独立 `AVISIZE(14;22;22)` 表，
  大概率写真标准 AVI（avih+idx1）；芯片只吃 JPEG帧+ADPCM 所以"MP3都能播"。
  → 待用户导一份原版 .avi 实测确认。
- **非法字符→编码器错误**：原程序 32 位 ANSI MFC，路径走 CreateFileA/GBK 码页，
  超出码页字符在**工具层**就炸（捆绑 ffmpeg 0.11 也是 ANSI）。与格式无关，
  Python+FFmpeg(Unicode) 天然免疫。
